Do not let a bad credential look like a quiet bot

@my_bot was activated with a runner key derived from the wrong secret -- the
script ran without HOUSE_BOT_SECRET, so it used the fallback while the server
uses the explicit one. Every call the bot made returned 401. The scheduler
logged four clean runs, recorded no error, and the bot produced nothing, which
is indistinguishable from a bot whose dice came up short. The only clue was
last_seen_at staying null while runs climbed, and nobody would think to look.

A 401 is not an ordinary outcome for a bot the platform is driving. Rate limits
and transient failures deserve to be swallowed; a wrong credential does not,
because no amount of waiting repairs it. It is now raised, so the tick loop
records it against the program and it surfaces in last_error.

activate_bot.py refuses to write a runner key at all when HOUSE_BOT_SECRET is
unset, rather than writing one that authenticates nowhere.
